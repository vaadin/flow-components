### 1.7 Serializable

- All manager classes — `CellValueManager`, `CellSelectionManager`, `CellSelectionShifter`, `SpreadsheetHistoryManager`, `ContextMenuManager`, `SpreadsheetStyleFactory`, `ConditionalFormatter` — **explicitly `implements Serializable`** with `@SuppressWarnings("serial")`.
- `Spreadsheet` itself does not `implements Serializable` *directly*, but inherits it via `com.vaadin.flow.component.Component` and bears `@SuppressWarnings("serial")`. Flow may serialize component trees for session replication, so changes to instance fields (adding/removing, changing types) need to be evaluated for session-compat impact even if no `serialVersionUID` is set.
- Practical implication for refactors: when we extract an interface and change the **type** of a field on `Spreadsheet` or a manager (e.g. from `Spreadsheet` to `SomeNarrowInterface`), Java serialization treats this as a non-breaking change at the bytecode level only if the new type is itself serializable. **The extracted interface must extend `Serializable`** to keep the manager serializable end-to-end.

## 2. Proposed first vertical slice

**Recommendation: `SpreadsheetHistoryManager`** (over `CellSelectionShifter`).

### 2.1 Why this one, not the other

| Criterion | `SpreadsheetHistoryManager` | `CellSelectionShifter` |
|---|---|---|
| LOC | **247** | 890 |
| Distinct `Spreadsheet` members it touches | **5** + one pkg-private field | ~12 + heavy paths through `CellValueManager` & `SpreadsheetStyleFactory` |
| Touches the server↔client contract? | No (commands replay through Spreadsheet, but no direct setProperty/callJsFunction) | No directly, but reads `Workbook` via `getWorkbook()` and uses `getSpreadsheetStyleFactory().cellStyleUpdated(…)` |
| POI direct mutation | None (delegates to `Command.execute()`) | Yes — `Cell.setCell…`, `Row.createCell`, etc. |
| Coupling to other managers | Only `CellSelectionManager` (3 methods) | `CellSelectionManager`, `CellValueManager`, `SpreadsheetStyleFactory`, `SpreadsheetHistoryManager` |
| Has dedicated unit tests today? | No | No |
| IT coverage | `UndoRedoIT`, `CellShiftValuesUndoRedoIT` | `CellShiftingIT`, `RowShiftIT`, `CellShiftValuesUndoRedoIT` |
| Blast radius if we break it | Undo/redo silently misbehaves | Selection-drag / fill-down silently misbehaves *and* corrupts cell values |

`SpreadsheetHistoryManager` is the better starter slice: it is the smallest,
its surface to `Spreadsheet` is narrow and well-defined, it does not directly
mutate POI, and its failure mode is observable but does not corrupt user data.
`CellSelectionShifter` becomes a strong second slice once the pipeline is
exercised.

### 2.3 Proposed extracted interface

```java
package com.vaadin.flow.component.spreadsheet;

import java.io.Serializable;

import com.vaadin.flow.component.ComponentEvent;

/**
 * Narrow view of {@link Spreadsheet} that {@link SpreadsheetHistoryManager}
 * needs. Introduced to break the bidirectional coupling between the
 * Spreadsheet god class and its history manager.
 *
 * <p>This interface MUST extend {@link Serializable} so the manager keeps
 * its Vaadin-session serialization contract.
 */
interface SpreadsheetHistoryHost extends Serializable {

    int getActiveSheetIndex();

    void setActiveSheetIndex(int sheetIndex);

    boolean isRerenderPending();

    /**
     * Replaces the package-private field write
     * {@code spreadsheet.initialSheetSelection = …}.
     */
    void setInitialSheetSelection(String address);

    CellSelectionManager getCellSelectionManager();

    /**
     * Pass-through to {@code Component.fireEvent}. Exposed here so the
     * manager doesn't depend on the full Component API surface.
     */
    void fireEvent(ComponentEvent<?> event);
}
```

Notes / choices to confirm before extraction:

- **Package-private visibility** is intentional — this is an internal collaborator, not a published API.
- We could go narrower and inline the three `CellSelectionManager` methods into the host interface, but that hides a more honest dependency. Phase-1 keeps the existing collaboration.
- `setInitialSheetSelection` is a new public-facing method on `Spreadsheet`. Adding it does **not** change the server↔client contract; it only replaces a direct field write. The field stays where it is; the setter is a small wrapper. This is behavior-preserving.

### 2.4 Test plan (Stage 3–4 for this slice)

Before *any* code move, we put a characterization net in place. Order matters.

1. **Headless server-side unit test for `SpreadsheetHistoryManager` (new).** Build a real `Spreadsheet` over a small in-memory xlsx, drive it through public API (`new Spreadsheet()` → seed cells → mutate → assert against `getSpreadsheetHistoryManager()`). Capture:
   - `addCommand` / `clear` / `setHistorySize` semantics including the edge case `commands.size() > historySize` *not* incrementing `historyIndex` (this is a subtle bug-shape that the methodology calls out as the kind of thing to PIN, not fix).
   - `canUndo` / `canRedo` boundary states (-1, 0, max).
   - `undo` / `redo` happy path with a `ValueChangeCommand`, asserting cells reverted and `CellValueChangeEvent` was fired.
   - `undo` / `redo` with active-sheet swap (`makeSureCorrectSheetActive`) — assert `getActiveSheetIndex()` flips and `initialSheetSelection` is set.
   - `undo` / `redo` with paint range vs single-cell selection (`changeSelection`).
2. **Differential / golden-master payload capture (new).** Drive the same scenarios as #1 against a `Spreadsheet` whose `Element` has been replaced with a recording proxy. Snapshot the sequence of `setProperty(name, value)` / `callJsFunction(name, args)` invocations. These are the bytes the client would actually see; if they don't change under refactoring, the contract is preserved.
3. **Confirm relevant IT pass on `bccb70fdef`.** Run `UndoRedoIT` and `CellShiftValuesUndoRedoIT` in isolation. If either is red on baseline, we have a pre-existing flake to address before we declare the slice characterized.
4. **JaCoCo coverage gate (new).** Add JaCoCo to the unit-test run. Require ≥ 95 % line coverage on `SpreadsheetHistoryManager` from #1 before we touch the file.
5. **(Optional, recommended) PIT mutation gate.** Run PIT on `SpreadsheetHistoryManager`. A mutation score < ~80 % means the tests don't actually *detect* changes and we need more assertions before refactoring.

## 5. Risks specific to this codebase (above and beyond pipeline §3 stage 6)

- **`@SuppressWarnings("serial")` everywhere.** No `serialVersionUID` declarations. Field-shape changes (including type changes through interface extraction) can break Vaadin session replication silently. Mitigation: keep new interfaces serializable; if a future slice changes a *field's serialized name or default value*, audit explicitly.
- **Package-private field writes.** `spreadsheet.initialSheetSelection` is written from three sibling classes. Other managers may also write package-private state in the same way; a global grep is owed once we start the second slice. (Identified so far: only `initialSheetSelection`.)
- **`static` collaborators.** `SpreadsheetFactory.logMemoryUsage()` is called from `SpreadsheetHistoryManager`. Static calls fall outside the extract-interface approach. They are not part of the coupling we're trying to break, but they should be documented when we touch a class. (No action required for slice 1.)
- **Flow-specific dispatch through Spreadsheet (`@DomEvent`).** Any "dead" code reachable only from the `SpreadsheetServerRpc` interface implementation is statically dead-looking but actually called from the browser. Pipeline rule #5 applies — do not delete based on static analysis.

## 6. Improvement suggestions for the pipeline document

These are things we learned in Stage 0 that the methodology should incorporate
for the next codebase / next operator. Update this list as more comes up.

> **Status note (2026-06-04).** All §6.1–§6.3 items below have been folded into
> `LEGACY_REFACTOR_PIPELINE.md` — see its §9 revision-history entry. This
> section is preserved as the *record of what we learned*, separate from the
> normative methodology. Add new findings here when they surface; promote them
> into the pipeline doc once they've proven out.

### 6.1 Things that worked well

- **§2 discovery checklist** is precisely the right shape. Following it produced a usable Stage-0 report in under an hour of agent work without writing any code. The "produce a written report, *then stop*" gate is valuable — it forces an alignment moment before commitment.
- **The "frozen contract list" framing** (rule #2) is concrete and reviewable. Once you write it down, every later "is this a refactor?" question becomes mechanical.
- **The IDE-refactoring-first stance** in §4 is the right default for a codebase this size. Free-text edits are the dominant source of accidental behavior change in any human refactor.

### 6.2 Things the methodology got slightly wrong (Flow-specific surprises)

- **Pipeline §1 / §1.5 assume the Flow port has a TS/Lit client.** Vaadin Spreadsheet (Flow) actually still uses **GWT** behind the Lit shim. The "frozen contract list" therefore has three layers (element properties, `callJsFunction` names, `spreadsheet-event` discriminator strings), not two. → Suggested edit: §1 should say "client may be Lit, GWT-compiled, or hybrid; do not assume."
- **Pipeline §1 says "SharedState + RPC is gone in Flow."** Not in this module — the `client/`, `shared/`, `rpc/` packages of legacy Vaadin-8 types are preserved and used by the GWT widget; `SpreadsheetHandlerImpl implements SpreadsheetServerRpc`. → Suggested edit: §1 should note "legacy SharedState/RPC types may be preserved as DTOs; check before assuming they're gone."
- **Pipeline §5 lists `CellSelectionShifter` as a viable first slice.** In this checkout it isn't — its surface is ~3× larger than `SpreadsheetHistoryManager` and it directly mutates POI. → Suggested edit: §5 should say "default candidate is `SpreadsheetHistoryManager`; downgrade `CellSelectionShifter` to second slice."

### 6.3 Things the methodology should add

- **A Stage-0 "find the real history repo" step.** When the codebase was *migrated* from somewhere else, `git log` in the current repo only shows post-migration commits. Stage 0 should explicitly ask: "Was this code born here? If not, where did it come from?" For Vaadin Spreadsheet the answer is [`vaadin/spreadsheet`](https://github.com/vaadin/spreadsheet) (Vaadin-8 / GWT add-on); the legacy bug-fix history that Stage 3 wants to mine for edge cases lives there, not here. → Suggested edit: §0 / §2 add a checklist item "ancestor repo, if any."
- **A Stage-0 "test-baseline capture" step.** Before any code change, run the unit suite once on the pinned commit and record the output. Today this is implicit in §2; making it an explicit Stage-0 deliverable would close a small gap. (We did this for unit tests here: 255/0/0/4. We have not yet for IT — that is a real gap.)
- **A naming convention for the extracted interfaces.** This Stage-0 surfaced "what's a good name for the narrow view of `Spreadsheet` that `HistoryManager` needs?" Proposed convention: `<Manager>Host` (e.g., `SpreadsheetHistoryHost`, `CellSelectionShifterHost`). → Suggested edit: add to §3 Stage 1.
- **A Serializable rule.** Stage-0 found that every manager `implements Serializable`. Any narrow interface we extract has to be `Serializable` too, or session replication breaks silently. → Suggested edit: §3 Stage 5 / §4 should call this out as a *rule*, not a corollary.
- **Explicit acknowledgement that "checkout reality" can move the boundaries of stages 0–1.** We did Stage 0 + a slice of Stage 1 (the members-used set for slice 1) before stopping. The methodology nominally separates them; in practice the smallest sensible STOP point includes the slice-1 members-used set, because Ugur needs it to approve the slice. → Suggested edit: §3 stage 0/1 boundary should say "for the *first* slice's manager, do the Stage-1 enumeration here; for the rest, defer."
- **A "language-agnostic substrate" plan.** The current methodology calls out `scip-java`, `jdeps`, `Spoon`. These are Java-specific. For the methodology to generalize to TypeScript / Python / Go / etc., Stage 0 should name the equivalent tools per ecosystem (e.g., `ts-morph` + `madge` for TS; `Pyright` + `pydeps` for Python; `gopls` symbol index + `go list -m` for Go).
- **A "dual-engine ports" pattern.** Vaadin Spreadsheet's Flow port preserved the GWT client — a hybrid that the methodology doesn't anticipate. This pattern is common in legacy migrations (a wrapper around a frozen old engine). → Suggested edit: §1 should add a sub-section "When the legacy engine is preserved beneath a new shim, treat its bytes as immutable; refactor only the shim and the server side."
